# AI Coding Vibe Flow v2 — 执行规范

版本：2.0 · 修订日期：2026-09-12

## 0. 目标和边界

服务于 GPT 网页版 Pro、Codex Pro 20x、ZCode/GLM 老套餐与 GitHub 开源仓库的协作。目标是减少人工搬运与失败返工，不是节省全部 Codex 额度，也不是为了用满额度制造任务。

GPT 负责目标和阶段验收；Codex 承担复杂实现、根因调查和独立审阅；ZCode 承担边界清楚的开发、机械修改、明确整改；CI 提供机械事实；人负责意图、风险授权和异常。

**规范、会话内执行、跨工具调度、GitHub 强制门禁是四件不同的事。** 本包提供前两者的协议和模板，不包含调度守护进程，不会因写了 AGENTS.md 就启动其他应用。[S2][S3][S5]

## 1. 最短主流程

```text
人给目标
 → 小任务直接执行；跨模块/多 PR 任务由 GPT 规划
 → Codex 校准真实仓库与难度（中高难时；不重复写一份大计划）
 → 一次规划依赖队列，只细化即将执行的 1–2 个任务
 → ZCode / Codex 领取各自可执行的任务
 → 一个语义 PR，内部 checkpoint 分段实现与自测
 → 最低验证 → 独立审阅（按门禁）→ 整改 → 新 SHA 验证与增量复核
 → 满足真实门禁才合并
 → 一个目标或里程碑完成后 GPT 按证据验收
```

人不用逐文件指挥。没有跨工具调度时，仍需启动相应会话或转交一次任务；不能把这说成完全无人值守。

## 2. 难度与风险分开

### 2.1 难度决定谁实施

| 难度 | 判断 | balanced 默认路由 |
|---|---|---|
| L1 | 文案、局部机械改动、明确格式修复 | ZCode |
| L2 | 一个模块内、方案清楚、可直接验证的开发 | ZCode |
| L3 | 跨模块、状态/数据流、未知根因或需要方案判断 | Codex；仅在方案和边界清楚时委派 ZCode |
| L4 | 复杂状态机、架构边界、并发/同步、深入调查 | Codex 调查并实现 |
| L5 | 系统级难题、多重约束、验证特别困难的大变更 | Codex 分阶段解决；独立审阅与专项验证 |

不再用 C+2R+V+K 的单一分数决定一切。分数的相同总量不能区分“很难但低风险”和“很简单但会删数据”。难度仍由 Agent 判断并用一句话给出理由，避免评分表本身变成人工负担。

### 2.2 风险决定怎么验收和合并

| 风险 | 典型 | 默认门禁 |
|---|---|---|
| R0 | 不改变运行时行为的非执行性文档等；不涉及安全政策/构建配置 | 自检、适用 CI；仅明确白名单才可考虑自动合并 |
| R1 | 可逆的普通行为变化，有可重复验证 | 自检、CI、独立审阅；后续可授权自动合并 |
| R2 | 持久化/数据模型、兼容公共接口、同步一致性、核心用户路径 | Codex 独立审阅、集成/兼容证据；默认人工合并 |
| R3 | 认证/权限/安全边界、不可逆迁移、删除数据、破坏兼容、CI/发布/合并信任策略 | 专项安全/迁移验证、必要时合并前产品验收；人工合并；真实数据操作另行授权 |

风险按内容判断，路径表只用于触发检查。只要涉及信任策略，即使是 `.md` 文本也不能按 R0 放行。一个 10 行权限修复可以是 L2/R3，一个难算法实现可以是 L4/R1。

初始项目未配置、验证不足或真实风险不明：禁止自动合并，先澄清技术事实。实施前与 PR Ready 前分别判断；审阅者可再次升级。

## 3. Codex 用量档位

默认 `balanced`：L3 中的根因、跨模块和状态逻辑交 Codex；ZCode 做明确施工；R1+ 有独立审阅。不能因为 Codex 是稀缺资源，就把全部 L3 都压给 ZCode。

`throughput`：额度充足且交付需求明确时，更多 L2 直接交 Codex以减少交接，优先推进真实积压；不主动制造架构重构。

`save`：L1/L2 全部 ZCode；L3 优先由 Codex短调查后委派；高风险审阅不取消。额度不足以完成必要审阅时暂停合并，而不是降门禁。

模式切换只调整执行者与调查投入，不调整安全标准。配额未知就保持 balanced；只有用户提供用量或已验证接口可读取时才动态调整，不声称自动知道剩余额度。

**区分普通网页聊天与 Work：官方当前说明 Work 与 Codex 共享用量，不得把切到网页版 Work 当成独立免费额度池。** 具体以账户 Usage 页面为准。[S6] 不在流程中硬编码套餐价格、任务条数、未来重置时间或老套餐权益。

## 4. 规划与 PR 粒度

一个 PR = 一个可独立验收的语义变化，不规定至少多少文件、多少行或至少几个 PR。能一个 PR 完成就一个，复杂目标给完整依赖图；后续任务可保持概略，不先写几千行过时施工计划。

一个中型 PR 内部可划 2–5 个 checkpoint，每段都能说明已完成行为和相关测试；checkpoint 是同一分支内的工作段，不要求每段独立 PR。

超过约 1,000 行人工维护的 diff 或 15 个逻辑文件时，仅触发一次范围审查，不作为禁令；生成物/锁文件/机械变更单独说明。拆分理由应是独立验收、不同风险/审阅领域或恢复能力，而不是数字。

遇到前置 PR 变化：重新读取最新基线，更新后续任务的合同/依赖。默认不做 stacked PR；依赖未合并的任务进入 BLOCKED。确需堆叠时必须记录 base branch 和后续 retarget/retest，不能误关 Issue或合错分支。

## 5. 任务合同与状态

优先用 GitHub Issue。每个任务记录 Goal、Scope、Out of Scope、带编号的验收标准、基线、依赖、难度/风险、负责人、验证策略及必要的回滚方案。验收标准要可观察，包含重要失败路径；“CI 全绿”不能代替功能验收。

Issue 上追加结构化状态更新；PR 上保存代码/CI/审阅证据。只读状态摘要不是另一份独立真相；避免 Issue、labels、本地看板三处各管一套状态。模板见 `templates/STATUS.example.json`。

```text
PLANNED → READY → RUNNING → VALIDATING → REVIEW → FIXING
                                      ↑          ↓
                                      └──────────┘
               → MERGE_READY → MERGED → ACCEPTED
```

任一阶段可转 `BLOCKED / HANDOFF_REQUIRED / HUMAN_REQUIRED`；已合并任务可在阶段验收后标记 `FOLLOWUP_REQUIRED`，但不能倒写为从未合并。

状态变化由真实事件驱动，不由 Agent 口头宣称。`MERGE_READY` 是候选状态，不是 GitHub 授权；`MERGED` 必须从 GitHub 实际结果确认。

避免 SHA 自引用：最终 head SHA、review/CI 链接写在 PR 评论、Issue 状态或运行产物，不为“更新本提交的 SHA”再提交一个新 commit 形成无限循环。

## 6. 批量执行与交接

默认同一个共享工作区只有一个写入者。Codex/ZCode可以各运行独立任务，但需不同 worktree/分支、无文件或语义依赖冲突；共享锁文件、schema、核心抽象变更默认串行。

选择顺序：已合并依赖满足 → 没有其他领取者 → 分配给当前 Agent → 优先级最高。领取者、run ID、基线和下一动作写回 Issue。无可靠锁/调度器时不得宣称实现了原子领取；多会话并行必须有明确不重叠的任务分配。

当前任务做到可验证边界后再推进下一个任务。不支持通知/守护调度时，完成当前可执行队列就结束并汇总，不无限轮询，不声称后台会自动继续。

跨 Agent 必须用交接单：Issue/PR、分支/head/base、已完成事项、实际失败日志、已尝试方案、剩余范围、下一动作、验收标准。传结构化结果而不是整段聊天。

调用下一 Agent 的工具不可用：写 `HANDOFF_REQUIRED` 并指定接收者；技术问题能自行处理就继续，不因此问人代码怎么写。涉及登录/授权/工具启动时，汇总为一次操作提示。

## 7. 验证不等于勾选

先记录目标分支基线。baseline 已红时，区分旧失败与新增失败；不得以“以前也坏”掩盖新回归或声称完整 CI 通过。未获认可的失败基线禁止自动合并。

每个 AC 对应证据：回归测试、接口响应、真实浏览器/E2E路径、截图或迁移演练。UI改动不能只靠 build；数据行为不能只靠 mock。未运行的关键验证标记缺证据，由合适 Agent 补，不默认让用户手工替测。

记录实际 command、cwd、exit code、日志/CI链接及关联 SHA。跳过、不适用、基础设施故障与通过分开。现有有效测试不能删掉、弱化或静默 skip来过关。

远端 CI 结果须覆盖最新 head；合并基线变化或 merge queue 产生集成提交时，另验证实际集成结果。[S4]

## 8. 独立审阅与修复闭环

实现者自检不能充当正式独立审阅。Codex 实现后可以由 Codex 在另一个干净会话/独立 GitHub任务审阅；新会话重新读取 diff、相关代码、Issue和测试，不把实现说明当作证明。

正式报告：reviewed head SHA、base SHA、审阅范围、AC逐项证据、findings、裁决。只允许：
- `PASS`：已检查约定范围，无未解决的阻塞项；
- `CHANGES_REQUIRED`：有应修复的阻塞项；
- `INSUFFICIENT_EVIDENCE`：无法核实必要范围或测试。

严重性与是否阻塞分开：P0紧急严重风险；P1高优先级明确问题；P2普通优先级问题；P3建议。所有P0/P1阻塞；P2中违反AC、可复现错误、安全/兼容问题同样阻塞；真正非阻塞的P2可有理由移后续。不能写 `APPROVE_WITH_P2_FIXES` 却在修复前放行。

默认一次完整审阅。整改后 reviewer核对新 SHA、每条已修问题和关联改动，不重新做一遍无关全库审美审阅。代码或配置又变更则更新验证；只改说明也要确认diff确实不影响代码，不能假装旧SHA等于新SHA。

GitHub 内置 Codex Review 当前侧重P0/P1，并不等于本规范的全量AC/测试缺口验收；需要这些检查时使用独立Codex任务的04提示词补足。无评论、一个👍、PR描述中的PASS都不自动等于 GitHub批准或可信状态检查。[S1]

## 9. 有限重试与止损

一轮失败 = 针对同一根因提出假设、实施修复并通过验证确认仍失败。正常开发中的首次红测试、发现新问题不自动计为“能力失败”。不能靠改命名来重置计数。

ZCode同一根因最多2轮有依据失败后交Codex；根因未知、权限/数据边界变化时可立即交接。Codex接手先重建最小复现，再最多2轮；仍无新证据则HUMAN_REQUIRED，附可选处置，而不是继续补丁堆叠。

CI基础设施故障最多做一次合理重试，仍失败转BLOCKED；审阅服务无响应转等待/交接，不生成虚假PASS。反驳finding需要证据并让独立reviewer核实，不能作者单方面把blocker删掉。

## 10. GitHub门禁与自动合并

初始 `auto_merge.enabled=false`，包括L1/L2。完成一轮真实闭环并核对仓库设置后，可以由维护者单独授权R0白名单、再扩到R1；R2默认人工，R3始终人工。

开启auto-merge必须同时满足：最新检查通过、审阅适用且有效、AC证据齐全、无阻塞finding、无human/blocked状态、非draft、分支保护成立、当前类别被授权。仓库还必须有可信强制门禁，不能只靠作者可改的labels或PR正文。

**本包不提供这样的远端强制门禁实现。** GitHub规则未配置或未验证时继续人工合并；阅读 docs/GITHUB_SETUP.md 决定后续实现范围。不能将本规范的条件句误认为现成脚本。

不要把Codex输出词直接解析成“管理员合并”。审阅身份、head SHA、检查来源、变更路径都要独立核实。高风险PR不能因为标成R0而自动放行；业务PR不能自己改门禁规则。

如果设置required approvals，确认真实审阅身份有资格满足它；同一GitHub用户的两个AI会话不能因此成为两个不同批准者。无需为表面自动化绕过平台审批限制。[S4]

GitHub auto-merge只会在已配置的required reviews/checks满足后执行，并不理解本工作流自定义风险等级。[S4][S7]

## 11. GPT最终验收只在合适位置

小型单PR任务：清晰AC、CI、独立审阅通常足够，不强制回GPT网页再走一次。

跨PR目标/阶段：GPT核对原始需求、完整PR清单、集成验证、用户路径证据和兼容性。高风险产品语义或不可逆决策在合并前验收；普通里程碑可在集成后验收。

结论是 `ACCEPTED / NOT_ACCEPTED / EVIDENCE_MISSING`，不是绕开工程门禁的MERGE授权。发现小修可形成后续Issue；关键目标未完成必须明确未验收，不把“代码已合并”视为目标完成。

## 12. 人真正需要做的事

默认日常：给目标、按需启动Agent批次、看一次异常汇总、批准高风险合并/真实数据操作。普通文件组织、局部实现、测试组织不要求人逐项选择。

HUMAN_REQUIRED仅用于：不同产品解释会明显改变行为；不可逆真实数据操作；新费用/密钥/账号；无法兼容的公共契约；安全披露；关键风险授权；Codex也已止损仍卡住。

缺工具、等待依赖和需要切应用不等于产品决策，但在assisted模式仍可能需要一次人操作，须诚实区分。

## 13. 效果反馈

按自然完成的每个里程碑或5–10个PR统计：人工介入次数、返工轮数、从任务到合并的耗时、合并后回归、Codex/ZCode用量（可得时）。据此调整路由，不以编造的模型胜率或固定额度比例分配任务。

审计只针对已确认的集成风险、近期回归和测试盲区；发现问题先形成有证据的Issue，不顺手大改。执行审计提示词不等于创建定时任务。

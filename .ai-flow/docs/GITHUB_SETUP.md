# GitHub 设置：哪些是真正门禁

本包没有改变你的仓库设置，也没有部署风险门禁。以下用于接入 Agent 根据真实仓库提出一次性设置清单。

## 第一阶段：人工合并，不增加付费服务

启用仓库现有CI并确认实际check名称；默认分支保护要求真实测试、必要lint/typecheck/build通过，阻止强推和直接写入，保护删除和敏感设置。不要机械填写不存在的检查名。

有正式review策略时，要求处理review对话，并考虑撤销过期批准或由非最后推送者批准最新变更。注意平台对作者自批和批准资格的限制：同一GitHub账户下的多个AI会话不等于多个独立身份。[S4]

保持个人Codex/pi + GLM登录留在本机；公开PR的CI不接触个人认证文件或生产密钥。首次演练：Draft PR → 真实CI → 独立审阅 → 整改 → 新提交CI/增量复核 → 人工Merge。

## Codex Review入口

先确认仓库已设置Codex cloud和code review。可通过PR评论`@codex review`发起审阅，也可按该仓库设置开启自动审阅；具体触发以当前产品设置和一次实测为准，不能假定“只有Ready且CI成功才触发”。[S1]

为避免无效提前审阅，本流程默认人工/Agent在CI后主动触发；使用自动review时，需确认其是否提前运行，避免又手动重复触发一次。

内置GitHub review侧重P0/P1。04提示词负责完整AC/行为检查；可在一个独立Codex审阅任务内完成，不要求常规任务同时做两次相同审阅。GitHub留言/emoji不能擅自映射成required approval。[S1]

## 第二阶段：低风险自动合并（可选，另行授权）

GitHub auto-merge只等待仓库已经设置的required reviews和checks；不会原生执行本包的R0–R3规则。[S7] 要真正放行低风险而拦住高风险，必须有可信门禁并验证至少以下负例：

1. 没有review、review超时或review来源不可信，不能放行。
2. reviewed SHA不是当前head、修复后没复核，不能放行。
3. 权限/数据/CI等敏感diff却填R0或改标签，不能放行。
4. 必需CI缺失、跳过、失败、作用在旧head或过时合并基线，不能放行。
5. 当前PR修改门禁脚本/合并规则，不得使用它自己提交的新规则给自己放行。
6. fork PR、注入式评论或重复webhook不能获取写权限或重复合并。
7. 有P0/P1或AC正确性P2未解决，不能放行。

可信自动化组件应从受保护策略读取配置，使用最小权限和限定范围的App身份；必要时固定required check来源。写令牌与运行不受信任代码隔离。不应在pull_request_target上下文检出并执行不受信任PR代码。自动合并必须验证head并考虑并发更新。

**这部分是未来组件的验收要求，不是本包已经交付的GitHub Action。** 尚无可信组件时，继续人工合并，不能把一个模板脚本或勾选框当安全边界。

R2默认人工合并；R3永不无人授权合并。合并、发布和操作真实数据库是三个不同权限，不自动串联。

## 接入后让Agent只给用户一页设置结果

每项列“已验证 / 未设置 / 无权限 / 不适用”，附真实check名、所需设置和一次验证方式。对于会改变审批策略或访问权限的操作，在实施前需要维护者明确授权。

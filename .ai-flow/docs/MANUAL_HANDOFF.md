# v4.0：怎样让进度可控

## 每一侧的结束边界

| 当前角色 | 这一轮做什么 | 何时停 | 给用户什么 |
|---|---|---|---|
| 网页版 | 阅读仓库、规划、写必要 Issues | 任务合同已写入或明确写入失败 | 主 Issue 与 Codex 入口 |
| Codex | 校准、调查、复杂实施、接收与技术把关 | 需施工、独立审阅、等待、决策或合并 | 本轮结果、下一角色、对应短句 |
| zcode / pi | 当前交接内实施与自测 | 完工、受阻、超范围或用户收尾 | 结果/阻碍评论和返回 Codex 的短句 |
| 独立 Codex reviewer | 只读审阅当前 SHA | 有明确结论或缺证据 | PR 审阅记录和返回负责会话的短句 |

**短句不是远程命令，不会发消息或启动程序。** 你在接收工具里粘贴并发送后，该侧才开始。本包不展示其他工具的实时进度；你直接在自己启动的窗口查看。

## 交接质量要求

一个可定位的 Issue 评论胜过一堆聊天记录。评论需有唯一交接标识、明确范围、分支/当前 SHA、改动归属和下一动作。施工结果引用同一标识和具体评论，避免回传错阶段。

正常只复制短句。无法把摘要发布到 GitHub 时，必须额外复制未发布摘要或先补发评论；不能承诺无权限场景仍只需一句话。不得把凭据、机器私密路径、原始敏感数据写到公开评论。

Codex 的施工交接固定附三条短句；施工者结束固定附返回 Codex 的一句。需要独立审阅时标明“请新开独立 Codex 会话”，不能让原实现对话直接自审。

## 为什么停在边界而不是等下一侧

上一侧把本轮事实写清并停止写入，你再决定是否启动下一侧；避免两个窗口同时改文件，也避免一侧耗额度等待另一侧。遇 CI 或依赖未完成同样输出准确恢复条件后结束，不轮询。

人工控制不意味着你要判断每个文件怎么改：复杂调查、任务分类、可执行的下一步仍由 Codex 决定。你负责启动和交接，普通技术选择留在当前 Agent 内。

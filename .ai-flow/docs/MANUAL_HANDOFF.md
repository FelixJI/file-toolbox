# v4.0：怎样让进度可控

## 每一侧的结束边界

**先判断 actor，再判断是否停止。阶段/检查点结束本身不是停止条件。**

| 当前 actor | 同 actor 时怎么做 | 何时才停 | 给用户什么 |
|---|---|---|---|
| 网页版规划者 | 在当前规划范围内继续读仓库、整理/更新 Issues | 规划完成要交 Codex，或需要用户补权限/决策 | 主 Issue 与 Codex 入口 |
| Codex 主执行 | 调查→设计→实现→测试→修复→更新证据可连续完成 | 换 zcode/pi、换独立 reviewer、等待外部条件、用户决策/授权、人工合并或超出当前授权 | 真实状态 + 对应短句/恢复条件 |
| zcode / pi 施工者 | 在同一 Handoff 范围内实现→自测→修复可连续完成 | Handoff 范围完成、受阻、越界或必须回 Codex 判断 | 结果/阻碍评论 + 返回 Codex 的短句 |
| 独立 Codex reviewer | 在只读审阅范围内连续检查与补证据判断 | 得出结论或缺证据；后续实现必须回 Codex 主执行 | PR 审阅记录 + 返回负责会话的短句 |

`current_actor == next_actor` 且仍在当前授权范围时，**继续执行**：不建 Handoff、不生成“重新启动我自己”的提示词、不停止。`current_actor != next_actor` 时才需要人工交接。Codex 主执行与独立 Codex reviewer 是两个不同 actor，即使工具名称相同。

**短句不是远程命令，不会发消息或启动程序。** 你只在跨 actor 或恢复外部等待时粘贴短句。本包不展示其他工具的实时进度；你直接在自己启动的窗口查看。

## 交接质量要求

一个可定位的 Issue 评论胜过一堆聊天记录。评论需有唯一交接标识、明确范围、分支/当前 SHA、改动归属和下一动作。施工结果引用同一标识和具体评论，避免回传错阶段。

正常只复制短句。无法把摘要发布到 GitHub 时，必须额外复制未发布摘要或先补发评论；不能承诺无权限场景仍只需一句话。不得把凭据、机器私密路径、原始敏感数据写到公开评论。

Codex 的施工交接固定附三条短句；施工者结束固定附返回 Codex 的一句。需要独立审阅时标明“请新开独立 Codex 会话”，不能让原实现对话直接自审。

## 为什么只停在“异主体边界”

人工控制的是 **Codex ↔ worker ↔ 独立 reviewer ↔ human/external** 的切换，不是每个内部步骤的 Continue 按钮。同一主体只要仍在授权范围，就应连续做完能做的工作；只有换主体时，上一侧才把事实写清、停止写入，由你决定何时启动下一侧。这样既避免两个窗口同时改文件，也不会把一个主体自己的调查、编码、测试拆成多次人工重启。

遇 CI 或依赖未完成，只有当它真实阻塞后续工作时才输出准确恢复条件后结束，不轮询；仍可安全推进的同主体工作应先继续。人工控制也不意味着你要判断每个文件怎么改：复杂调查、任务分类、可执行的下一步仍由 Codex 决定。
